## Подтверждённые ошибки

### 1. P2 — заявленный сквозной путь live→БД→двойник не реализован

**Цепочка:** `backend/app/live.py:93` → `ingest():61` → обновление памяти `:73–81` + INSERT/commit `:87–89`. `/status` (`:100–107`) читает память; `frontend/src/LivePanel.tsx:17–21` опрашивает её раз в 1,5 с. Обратного читателя `events/live_*` в runtime нет.

Двойник идёт другой цепочкой: `frontend/src/TwinPage.tsx:95` → `backend/app/sim/api.py:145–160` → `simulate(twin_overlay(_scenario(...)))`. KPI вычисляются из результата симуляции (`backend/app/sim/kpi.py:147–172`), кадры питают план (`frontend/src/twin/Plan2D.tsx:31`), схему (`Flow2D.tsx:63`) и 3D (`Scene3D.tsx:393`). Прогноз/тревоги получают эмулятор: `backend/app/learn/forecast.py:98`, `learn/alerts.py:46`, `learn/stream.py:33–34`.

**Расхождение:** `docs/INTEGRATION.md:12` заявляет журнал→SimPy→LightGBM, а `:52` — демонстрацию целого пути. `ARCHITECTURE.md:46–47` и `frontend/src/arch/model.ts:42` изображают этот мост без ограничения для live. Архитектура есть; нет именно заявленного сквозного поведения.

**Воспроизведение:** получить `run_payload('base',7)`, передать через `post_events` остановку paint, 1000 годных на qc и дефект paint, повторить расчёт сначала с кешем, затем после `run_payload.cache_clear()`. Получено: accepted=3, SQLite live_rows=3, live good=1000, defects=1, paint=down; **KPI и все кадры равны исходным даже без кеша**. Следствие: реальная остановка/качество/выпуск не меняют расчёты и тревоги двойника. В новом процессе live status также возвращает good=0/events=0 при трёх сохранённых строках: восстановления панели из событий нет.

**Опровержение альтернатив:** отдельный канал камеры действительно влияет на двойник (`learn/api.py:247–261` → `Calibrator.add_camera` → `sim/api.py:32–54`), но `/live/events` этот канал не вызывает. Загруженные факты входят через `fact_days.params` (`fact_days.py:89–101`) и `_scenario` (`sim/api.py:84–90`), а не через live. Поэтому «никакие внешние данные не поступают в двойник» неверно. P2 относится к описанному пути; общего high-нарушения ТЗ из отсутствия PLC не следует.

### 2. P2 — автокалибровка загруженного файла не восстанавливается при старте

**Цепочка:** `/api/data/activate` (`backend/app/data_api.py:31–34`) → `dataset.activate` (`dataset.py:68–74`) сохраняет файл и выбор → `_reload` (`:122–130`) вызывает `calibrate`. Подгонка меняет `BASE.stations`: брак `:98–102`, надёжность `:105` → `twin_calib.py:77–78`, циклы `dataset.py:110–116`.

После нового запуска `BASE` заново строится из line.json (`backend/app/sim/params.py:15–16,78–85`). `active_facts` (`dataset.py:38–46`) читает выбранный файл **без подгонки**. Startup только запускает прогрев (`main.py:73–78`); его шаги (`:52–62`) не вызывают `_reload/calibrate`. Других callers `calibrate/_reload`, сериализации этих параметров или читателя `twin_params` не найдено.

**Воспроизведение:** в процессе A активировать `make_xlsx(paint_defect=0.08)` из `backend/tests/test_real_data.py:14`, добавить ручной ввод 100/20 и 20 событий камеры; в процессе B открыть ту же БД и активный набор, рассчитать base/seed=7. Файл остаётся активным (`is_test=false`), но calibration становится null; цикл paint **3.831488→3.68**, MTBF paint **12739.639→1100**, MTBF assembly **20181.253→1000**. Выпуск двух смен **244→251**, версия **8fcef298ff→2111920814**, без новых фактов. Последствие: сохранённый набор и факты остаются, а прогнозы/what-if снова используют исходные циклы и надёжность.

**Опровержение альтернатив:** ручной/камерный байес восстановился: mean **0.09226841721371262** одинаков, camera_seen=20. Реальный мост БД→двойник существует: `learn/api.py:43–47,64–81` проигрывает `learning_log`; `sim/api.py:32–54` применяет оценку. Потерю **всей** калибровки отвергаю. `backend/tests/test_learn.py:111` проверяет этот replay, а `test_real_data.py:44` — activate/reset в одном процессе; автоподгонку после настоящего нового процесса они не проверяют.

### 3. P2 — нечисловой good принят схемой и ломает пакет после изменения памяти

`backend/app/live.py:43–44` допускает `value: str | float | None` для любого типа события. Для good нет отдельной проверки; `ingest` сразу выполняет `int(float(...))` (`:74–75`). `post_events` (`:93–97`) не перехватывает ValueError. INSERT находится после обработки всего пакета (`:86–89`).

**Воспроизведение:** `Batch(events=[{'station':'qc','type':'good','value':3}, {'station':'qc','type':'good','value':'oops'}])`, затем `post_events(batch)`. Pydantic принимает пакет; второе событие вызывает ValueError; первое уже изменило good/events в памяти, но его строки в SQLite нет (проверено: good=3, events=1, db_rows=0). Через HTTP неперехваченная ошибка означает серверную ошибку вместо rejected/422. Последствие: потерянная запись и расхождение панели с БД; повтор пакета может повторно увеличить счётчик. Проверки неизвестных участков/состояний (`:66–72`) этого случая не покрывают. Связано с обещанием отсеивать мусор (`ARCHITECTURE.md:57`) и достоверностью мониторинга; не отдельное требование промышленного шлюза.

## Схема БД и отвергнутые выводы

- **live→db работает полностью как запись:** `db.py:21–28` задаёт events, а `live.py:87–89` пишет и коммитит. Отсутствие downstream-потребителя не делает саму запись «partial».
- **db→twin не отсутствует целиком:** learning_log содержит ручные/камерные уроки и восстанавливается. Таблица `twin_params` (`db.py:40–43`) объявлена, но не является механизмом восстановления; нельзя судить только по её наличию или пустоте. `forecasts/model_versions` также объявлены в схеме; утверждение о реальной работе соответствующего хранилища требует отдельных писателей, а не CREATE TABLE.
- **Мониторинг загрузки/простоев/качества не отсутствует:** `TwinPage.tsx:174–182` показывает доли состояний и простой, `ZonePanel.tsx:40` — брак, `ShiftBuilder.tsx:144–146` — нормы, `Dashboard.tsx:18–35` — события и выпуск. Ограничение: эти показатели основаны на симуляции; текущий live status не содержит расчёта загрузки, длительности простоя или доли брака.
- **Неиспользуемый SSE не доказывает отсутствие near-real-time:** `/sim/stream` (`sim/api.py:224–235`) воспроизводит готовые кадры; LivePanel использует polling. Отсутствие EventSource, MQTT, TimescaleDB и физического PLC само по себе не нарушение данного ТЗ.
- **Архитектура решения предоставлена:** ARCHITECTURE.md и вкладка arch существуют. Подтверждены неточности отдельных связей, а не отсутствие архитектуры. Применение подгонки при enough_data=false само по себе не противоречит ТЗ: минимального числа записей оно не устанавливает.

## Воспроизведение и ограничения

Из корня проекта: `backend\.venv\Scripts\python.exe -B reports\audit-data-paths-repro.py`. Для одного случая входной валидации: добавить `--validation-only`. Скрипт вызывает фактические обработчики и расчёты, запускает новые процессы, использует собственные ALLUR_DB/ALLUR_STATE_DIR в временной подпапке reports и не меняет приложение/исходные данные.

Проверены альтернативные SQL-читатели, callers activate/reset/calibrate, startup/warmup, replay обучения, камера, fact_days, frontend readers. Это статический аудит и изолированные вызовы функций; браузер, живой HTTP-сервер, Docker, промышленная нагрузка и latency SLA не проверялись. Прогрев разобран по коду, в воспроизведении ALLUR_WARMUP=0. Не проверены остальные требования ТЗ. Общий near-real-time вердикт — **partial для заявленного сквозного пути**, не доказательство провала допустимого концептуального прототипа. Дополнительные независимые агенты здесь не запускались: этот отчёт — материал для отдельного refutation-agent.
