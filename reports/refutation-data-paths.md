# Refutation: три findings путей данных

Дата: 2026-10-08. Независимая статическая проверка reports/audit-data-paths.md и reports/audit-source-check.md по уже прочитанным callers/callees, startup и scope ТЗ.

| Finding | Вердикт | Severity |
|---|---|---|
| 1. Live → БД → двойник | **narrowed** | **P2** для заявленной интеграции |
| 2. Автокалибровка активного файла после старта | **retained** | **P2** |
| 3. Нечисловой good и частичная обработка пакета | **retained** | **P2** |

## 1. Live → БД → двойник — narrowed, P2

`backend/app/live.py:93–97` → ingest: изменение STATE (`:73–81`) и INSERT/commit (`:82–89`). Панель читает STATE через status (`:100–107`), polling работает (`frontend/src/LivePanel.tsx:17–21`). Поэтому отсутствие live-приёма или записи в БД **rejected**.

Обратного runtime-потребителя live-записей в просмотренном коде не найдено. Расчёт идёт через `backend/app/sim/api.py:145–160` → simulate(twin_overlay(_scenario(...))). Прогноз/тревоги используют emulate (`backend/app/learn/forecast.py:98`, `alerts.py:46`, `stream.py:33–35`). PLC-эмулятор сначала получает готовую симуляцию, затем шлёт её события в ingest (`live.py:113–129`): это обратное направление, не доказательство live → расчёт.

Контраргументы: DB → twin существует через learning_log replay (`learn/api.py:43–47,64–81`) и overlay (`sim/api.py:32–54`); факты дня входят через `fact_days.py:89–101` → `_scenario` (`sim/api.py:84–90`). Общее утверждение «внешние данные не влияют» **rejected**.

Последствие: live-остановка/выпуск/дефект обновляет отдельную панель и БД, но автоматически не обновляет KPI/прогноз двойника. `docs/INTEGRATION.md:9–16,51–52` описывает более полный путь; ссылка исходного аудита на :54 для обещания «целиком» неточна. Scope ТЗ допускает концепцию/прототип (`../handoff/AI_AGENT_CONTEXT.md:163–193`), физическое PLC не обязательно; live и шлюз помечены demo/plan (`frontend/src/arch/model.ts:36,40`). Поэтому общий провал ТЗ **rejected**, сохраняется узкое расхождение заявленной интеграции. Сброс live STATE после старта не выделен в отдельный finding.

## 2. Автокалибровка после старта — retained, P2

activate сохраняет файл и path/is_test/activated_at (`backend/app/dataset.py:68–74`), затем `_reload` вызывает calibrate (`:122–130`). Подгонка меняет BASE.stations: дефекты (`:98–102`), надёжность (`:104–105` → `twin_calib.py:77–78`), циклы (`dataset.py:110–116`). Эти параметры в active_dataset.json не сериализуются.

После нового процесса BASE создаётся из LINE (`backend/app/sim/params.py:78–85`); active_facts только читает файл (`dataset.py:38–46`). Найденные callers `_reload` — activate/reset (`:74,80`); calibrate вызывается в `_reload` (`:125`). Startup запускает прогрев (`backend/app/main.py:73–78`), шаги которого (`:52–62`) не вызывают подгонку. Диагностический fit использует apply=False (`data_api.py:57–60`). Таблица twin_params (`db.py:40–43`) сама по себе не восстанавливает параметры.

Контраргумент: начальные наблюдения Calibrator берутся из активного файла (`learn/calib.py:32–37,61–64`), ручное/камерное обучение восстанавливается (`learn/api.py:64–81`) и применяется overlay (`sim/api.py:38–54`). Day-сценарии сохраняют фактические дефекты/простои (`fact_days.py:95–101`). Потеря **всей** калибровки **rejected**.

Последствие: активный файл остаётся выбранным, но базовые/what-if расчёты теряют автоподогнанные циклы и надёжность; дефекты зависят от сценария и learned overlay. Без дополнительных уроков twin_context использует базовый paint.defect_p (`sim/api.py:38–40`). Сохранённый выбор и поведение модели после старта расходятся.

## 3. Нечисловой good — retained, P2

`backend/app/live.py:43–44` разрешает str/float/None для любого event type. Проверки участка/state (`:66–72`) не валидируют числовой good. На известном qc значение "oops" достигает int(float(...)) (`:75`); post_events не перехватывает ValueError (`:94–97`).

Пакет good=3, затем good="oops": первый элемент уже меняет good/events и добавляется в локальный rows (`:75–85`), второй прерывает обработку до INSERT/commit (`:86–89`). Если ошибочный элемент первый, частичного изменения памяти этим примером не доказать.

Последствие: неперехваченная ошибка запроса (обычно HTTP 500), изменённые счётчики без соответствующих строк БД; повтор пакета может снова увеличить память. Ранее committed записи не теряются. Схема и фильтры этот finding не опровергают; основание P2 — согласованность реализованного API, не промышленный SLA.
