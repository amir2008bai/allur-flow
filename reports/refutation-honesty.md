# Независимая refutation честности Allur Flow

2026-10-08. Прочитаны `audit-honesty.md`, `audit-source-check.md`, правила, PLAN/PROGRESS и соответствующие цепочки backend/UI. Исходные PDF/DOCX проверены главным агентом; здесь их содержание принято по source-check, повторного извлечения нет. Проверка статическая: численные воспроизведения первого checker не выдаются за собственные. Приложение не менялось, тесты/обучение/LLM не запускались. Пути относительно `allur-flow`; строки текущего checkout. Severity — риск достоверности вывода прототипа, не доказанный ущерб заводу.

## Вердикты по восьми находкам

### H1 — retained / high

**Опровержение:** API честно ставит `fact+sim` (`backend/app/journal.py:165`), смены имеют собственные источники (`:131,139`); UI различает факт/сим в строках (`frontend/src/twin/MonthJournal.tsx:212`). Следовательно, тезис о полном сокрытии смеси неверен. Альтернативный путь симулятора считает годные через `run.good_out` (`backend/app/sim/kpi.py:124,156–160`).

**Почему осталось:** DOCX-путь выбирает сборку (`backend/app/fact_days.py:25,133,152`) и подменяет ею good первой смены (`journal.py:136–140`), затем складывает со второй (`:144,168`). Календарная метка «факт» зависит от наличия данных, а не чистоты суммы (`MonthJournal.tsx:134`). Последствие: смешанный выпуск и измеренная сборка читаются как дневной выпуск годных ОТК; корректный симуляционный путь эту подмену не устраняет. Значения 239/224 здесь независимо не пересчитаны.

### H2 — narrowed / medium

**Опровержение:** время прямо названо допущением (`fact_days.py:27–28`), `why` передаётся вместе с простоем (`:135–136`; `journal.py:154–155`). Фактическими остаются оборудование, причина и длительность, а не всё событие выдумано. Отнесение к смене — воспроизводимая эвристика с допуском, а не случайное число (`fact_days.py:73–85`).

**Остаток:** эвристика утверждает «значит простой был» (`:77–78`), вставляет смену в «данные завода» (`:122–124`); составная запись получает `source=fact` (`journal.py:155`), описание — фактический бейдж (`MonthJournal.tsx:205`). Из недоработки участка нельзя доказать смену оборудования без дополнительных условий. Последствие: provenance фактической длительности распространяется на предполагаемую смену. Сужено до неверной атрибуции времени; high снижено из-за явной оговорки и сохранения исходных полей.

### H3 — retained / high

**Опровержение:** заводские точки имеют приоритет (`backend/app/spc.py:32–35`); API возвращает число фактов и оговорку (`:116–117`), UI показывает источники и различает точки (`frontend/src/twin/PaintSpc.tsx:33,48–49,72`). При наличии достаточной фактической истории существует корректный альтернативный путь без sim-точек.

**Почему осталось:** недостающие наблюдения заменяются симуляцией (`spc.py:36–40`), pooled/границы/сигналы не фильтруются по источнику (`:69–80,115`), рекомендации категоричны (`:91–98`). Черновик 8D переносит объединённую среднюю и стабильность как описание проблемы (`backend/app/capa.py:124–126,139`). Последствие: демонстрационная история определяет производственную рекомендацию. Наличие маркировки не является ограничением применимости вывода; число 20/2 и 4,641% принято из первого отчёта, заново не вычислялось.

### H4 — narrowed / medium сейчас; high при расширении фактов

**Опровержение:** sim в периоде после действия вызывает `demo/note` (`capa.py:111–114`), и UI отображает их (`frontend/src/twin/Capa8D.tsx:125`). Менее пяти дней дают wait (`capa.py:94–97`). На исходном DOCX есть только два фактических дня: ветка «пять fact после» из контрольного примера первого checker не является достижимой реальной историей текущего набора. Нельзя утверждать, что уже получено настоящее подтверждение действия на заводе.

**Остаток:** `_baseline` берёт fact/sim через `_day_point` (`capa.py:63–79`; `spc.py:32–40`), `before` теряет источник (`capa.py:91`), а demo зависит только от after (`:111`). Расширенный импорт с ≥5 fact после и sim до может получить confirmed без demo (`:103–114`). Последствие: будущая фактическая история сравнивается с искусственной базой как доказательство эффекта. Кроме того, формулировка закрепления действия (`:106`) сильнее результата теста долей: причинность не установлена. Контрольный вход — доказательство ветки, а не текущий инцидент.

### H5 — narrowed / medium

**Опровержение:** формула произведения выходов пригодна как модельная оценка RTY; есть `source=calc`, provenance и явное допущение независимости (`backend/app/findings.py:176–187`). Это не выдуманное число без основания и не установленная арифметическая ошибка.

**Остаток:** одинаковая когорта/первый проход не подтверждены исходником, а заголовок и текст описывают наблюдавшиеся кузова (`findings.py:184`; `backend/app/plain.py:49–52`). Последствие: условный RTY принимается за измеренную долю конкретных кузовов. Сужено до семантики и неполноты предпосылок, без запрета самой формулы.

### H6 — narrowed / medium

**Опровержение:** каскад явно симуляционный (`frontend/src/twin/LossCascade.tsx:77`), идеальный цикл обозначен допущением (`:23`; `kpi.py:172`), распределение по одновременности тоже оговорено (`kpi.py:108`; UI `:90`). OEE использует реальные события симуляции и good_out; A/P/Q и суммы построены согласованно (`kpi.py:124–144`). Для оценки вмешательства существует отдельный what-if (`backend/app/sim/api.py:197`).

**Остаток:** Q — произведение маргинальных долей, P — остаток, качественные потери распределены логарифмически (`kpi.py:129–139`), а UI называет их временем переделки и машинной/денежной потерей конкретной причины (`LossCascade.tsx:29,81–84`). `produced` растёт на обработке станции (`backend/app/sim/engine.py:165`), а не уникальном VIN. Последствие: условная декомпозиция читается как причинный эффект устранения потерь. Сужено до физической интерпретации; разность 92,202/92,063 и 21,312 здесь не воспроизведены и не являются самостоятельным доказательством дефекта OEE.

### H7 — narrowed / high

**Опровержение:** категоричное «нет сохраняемого журнала прогнозов» неверно: `journal.record` сохраняет весь record с forecast в SQLite и повторно его использует (`journal.py:131–133,175–186`). Replay действительно прогнозирует до отложенного обучения (`backend/app/learn/forecast.py:114–116,145–146,201–202`); ledger_size явно описывает симуляционный поток (`:235`). Target leakage в River не доказана.

**Остаток:** сохранение происходит при ленивой сборке истории; прогноз строится текущей версией двойника (`journal.py:117–140,182–184`; `sim/api.py:42,146`), может пересобираться при изменении фактов (`journal.py:178–182`). UI называет его «прогноз утром» и сверяет с заводом (`MonthJournal.tsx:171,208`). Поиск `forecasts|ledger|feature_cutoff|horizon_start` в app/scripts/tests нашёл схему `db.py:29–34` и ledger в памяти (`forecast.py:109,145,235`), но не запись SQL forecasts. Последствие: сохранён ретроспективный прогноз, нет гарантии предварительной регистрации на реальное утро. Сужено до отсутствия доказуемого прогноз→факт для исторического журнала; число пустых SQL rows независимо не проверялось.

### H8 — retained / medium

**Опровержение:** есть реальная проверка единиц/знака (`backend/app/copilot/agent.py:127–136`), серверные карточки из tool-results (`:140–145`), предупреждение UI (`frontend/src/Copilot.tsx:108–110`) и офлайн-ответы по шаблонам (`agent.py:256–352`); при ошибке LLM работает fallback (`:360–366`). Нельзя заключать, что внешняя LLM уже выдумала числа.

**Почему осталось:** целые ≤10 без единиц проходят без проверки (`agent.py:123–124`); ответ с unverified возвращается как обычный ответ (`:222–228`), fallback не включается от результата валидации. Чипы агрегируют источники функций (`backend/app/copilot/api.py:22–23`) и не привязывают утверждения к полям. Даже совпадение числа/единицы не проверяет предмет утверждения. Последствие: «Брак 7» может получить «числа проверены», а обнаруженная неподтверждённая цифра остаётся в ответе. Severity снижена с high до medium: доказан обход защиты, не фактический ложный ответ или ущерб.

## Итог и границы

**retained: H1, H3, H8; narrowed: H2, H4, H5, H6, H7; rejected: нет.** Широкие трактовки о сокрытии всех источников, отсутствии сохранения любого прогноза, отсутствии защиты 8D и математически сломанном OEE отвергнуты внутри соответствующих пунктов. Это не отменяет оставшиеся конкретные дефекты. Строки проверены чтением кода; браузер, расширенные импорты и численные сценарии не запускались. Отсутствие физического PLC не считается дефектом.
